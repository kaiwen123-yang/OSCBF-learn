## 原始顺序

以下相对时间使用同一主机的单调接收/调用时钟；北京时间列中，接收帧取 SocketCAN 时间戳，发送取 SDK 调用时刻，不把 SDK 调用时刻称为物理发送时刻。

| 第一条 ACK 错误，0x24 | 19:05:52.513301 | 0 ms |

ACK 错误先于 ENOBUFS 约 202 ms。证据支持“有效对端应答消失，发送无法正常完成，随后队列耗尽”的顺序；不能将缓冲区满直接解释为最初原因，也不能靠增大发送队列认定故障已解决。

Linux `CAN_ERR_ACK=0x20` 表示发送未获得 ACK；`0x24` 同时带控制器状态错误标志。接口由 ERROR-ACTIVE 变为 ERROR-WARNING，错误告警计数增量 7、被动错误计数增量 4864、bus-off 为 0。普通 `rx_errors/tx_errors` 为 0 与这些错误帧并不矛盾，不能据此称 CAN 正常。[Linux error.h](https://github.com/torvalds/linux/blob/v6.6/include/uapi/linux/can/error.h)、[SocketCAN 文档](https://docs.kernel.org/networking/can.html)

## 为何“已发送急停”不是可靠结论

固定 SDK 的 `CANComm.send()` 遇到 ENOBUFS/ENETDOWN 时保存 `last_error` 并直接返回，不抛出异常。原脚本在 `electronic_emergency_stop()` 返回后无条件写 `damping_emergency_stop_sent`，因此终端和 summary 的旧措辞过度确定。

`sdk_tx.csv` 中 0x150、`0100000000000000` 的 `comm_error_after_send` 明确为 ENOBUFS。此次请求未成功提交到正常发送路径，不能据此证明机械臂执行了电子急停。原始 summary 和 console 不改写；当前脚本只将记录改为 `requested` 并保存通信错误，没有新增检查门槛、重试、复位或使能。

已检查 SDK 的 `disconnect()` → `DriverContext.shutdown()`：它们关闭线程和 CAN 资源，没有发送 reset 或 disable。全程两个 0x471 都是 `0702000000000000`（全轴使能），唯一 0x150 是上述失败的 01 请求，没有 02 复位帧。因此不能用代理退出或用户操作解释后来的正常待机/六轴失能。

## 根因范围

1. **已证实的直接异常：** 正常报文停止且适配器连续报告 ACK 错误，随后发送缓冲区满。这发生在 MOVE_J 回零阶段，与 OSCBF 求解、夹爪阶段、新增到位检查无关。
2. **待区分的状态变化：** 控制器固件、保护/通信状态切换，或电源瞬态。后续恢复为六轴失能且 mode=0，与初始化后状态相容；用户补充指示灯没有变化，日志也没有重启计数或电源波形，不能写成已经证实掉电或重启，更不能据此要求更换电源。
3. **仍需区分：** CAN 接头/线缆/终端/收发器故障，或 USB-CAN 设备/固件异常。出错后主机仍收到大量适配器错误帧，所以“整个 USB 数据通道从开始就完全消失”不符合记录；这不排除适配器 CAN 侧故障。仅有主机一端记录不能进一步定位。
4. **供电证据边界：** 最后六轴驱动电压为 `[23,23,22,22,22,22] V`，状态位均为 0x40；部分轴相较初始低 1 V。这个采样没有捕获正常报文停止后的电压，不能据此证明或排除瞬间欠压。用户确认电源标称 24 V、指示灯没有变化；实际铭牌电流尚无记录，不能以手册要求替代实际规格。

本次 SDK 调用处的 realtime−monotonic 偏差范围仅约 0.000477 ms，未见上次 +2.390776 s 的跳时现象。此前时钟域修复继续保留；本次的 ACK 错误有独立原始证据。

MOVE_J 开始时存在两次目标发送紧接，组起始间隔 0.064693 ms；之后约 20 ms 一组。第一条 ACK 错误在该初始短间隔之后约 0.918 s，未紧随发生，当前没有证据将这次故障归为相同机制。这个旧 MOVE_J 入口与已修复的 CPV 10 ms 连续调度是不同路径，不能混为同一验证。
